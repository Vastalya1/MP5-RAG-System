MP5-RAG-System Technical Documentation
======================================

1. Purpose and Scope
--------------------
This repository implements a medical-insurance policy assistant built on a Retrieval-Augmented Generation (RAG) architecture.
Its main job is to:

- ingest policy PDFs into a searchable vector store,
- let admins and end users upload documents,
- answer policy questions with grounded context,
- maintain login state, audit logs, and query history,
- optionally fall back to Tavily web search for low-confidence results.

The current active runtime path is the OpenAI-backed path imported from the `_Chatgpt` modules. Despite the names, these modules are not tied to the ChatGPT product UI; they use the OpenAI Python SDK and `gpt-4o-mini` through Chat Completions.

This document covers:

- application architecture,
- code organization,
- startup and configuration,
- upload and query lifecycles,
- persistence layout,
- major data structures,
- frontend and backend behavior,
- evaluation and utility scripts,
- implementation caveats that affect real runtime behavior.


2. High-Level Architecture
--------------------------
The application has five main layers:

1. Web layer
   - FastAPI app in `src/frontend/app.py`
   - Jinja2 templates for login, dashboards, chat, shared library, and activity pages
   - Session-based authentication and CSRF protection

2. Ingestion layer
   - PDF text chunking from prose
   - table extraction from PDFs
   - table-to-natural-language conversion
   - embedding and storage in Chroma Cloud

3. Retrieval and answer layer
   - query rewriting
   - hybrid retrieval: semantic + BM25 keyword
   - metadata-aware reranking
   - LLM reranking
   - answer generation with citations

4. Orchestration layer
   - LangGraph-based classifier/router
   - direct-answer path for non-RAG queries
   - RAG path with optional query decomposition
   - optional Tavily fallback when retrieval confidence is low

5. Persistence and observability layer
   - PostgreSQL tables for users, uploads, audit events, query history
   - file storage under `dataset/`
   - application log and per-query lifecycle logs under `Logs/`

8. Application Startup Flow
---------------------------
Startup behavior is concentrated in `src/frontend/app.py`.

Startup sequence:

1. `.env` is loaded via `load_dotenv()`.
2. print interception is enabled through `capture_print()`.
3. FastAPI app is created.
4. request middleware is registered.
5. session middleware is added.
6. template/static directories are configured.
7. upload directories are created if missing.
8. lazy singletons are prepared for:
   - retriever
   - rewriter
   - reranker
   - answer generator
   - orchestrator
   - Chroma client
9. on FastAPI startup, `_init_db()` is called.
10. `_init_db()` creates tables and upserts default admin users.

Request middleware behavior:

- assigns a transaction id from `x-transaction-id` header or generates one,
- stores it in `request.state.transaction_id`,
- pushes it into a context variable for logs,
- logs request start and completion,
- adds `X-Transaction-Id` to the response,
- logs exceptions with timing and type.


9. Authentication, Sessions, and Security Controls
--------------------------------------------------
Authentication is session-based, not token-based.

Session behavior:

- `SessionMiddleware` stores the user object inside the signed session
- `same_site="strict"`
- `https_only` is env-controlled
- max age is env-controlled

User object stored in session:

- `{"username": ..., "role": ...}`

Password behavior:

- New users are stored with Argon2 hashes via `passlib`.
- Older PBKDF2 hashes are still supported for verification.
- On successful login of a PBKDF2 account, the password is transparently upgraded to Argon2.

Registration password rules:

- minimum length from `PASSWORD_MIN_LENGTH`
- must contain:
  - one lowercase letter
  - one uppercase letter
  - one digit

CSRF:

- every form POST is expected to carry `csrf_token`
- `_ensure_csrf_token()` creates a session token if missing
- `_require_csrf()` validates form token against session token
- CSRF can be disabled with `DISABLE_CSRF=true`

Lockout logic:

- failed attempts increment in `users.failed_attempts`
- after `MAX_FAILED_ATTEMPTS`, account is locked until `now + LOCKOUT_MINUTES`
- successful login resets `failed_attempts` and `locked_until`

Important behavioral note:

- Default admin users are seeded on every startup using `INSERT ... ON CONFLICT DO UPDATE`.
- That means the hardcoded default admin passwords are effectively reset on every app startup unless the code is changed.

Path safety:

- `_safe_file_path()` resolves paths and ensures the requested file is inside the intended base directory before serving/deleting it.

Log redaction:

- `src/shared/logging_utils.py` redacts:
  - password-like keys
  - bearer tokens
  - OpenAI keys
  - DSNs
  - generic long secret-looking tokens

-----------------------
Disk storage directories:

- shared uploads:

  - `Logs/application.log`
  - `Logs/queries/<query_id>.log`
  - `Logs/query_phases/<query_id>_lifecycle.txt`

Important implementation note:

- deleting a file from disk does not remove its embedded vectors from Chroma Cloud
- personal uploads remove previous local files from the user's folder before saving the new file
- however, there is no collection cleanup step that deletes old personal vectors from Chroma before re-ingestion
- so "one personal file per user" is enforced at the filesystem/UI level, not strictly at the vector-store level

16. Query Request Lifecycle
---------------------------
This is the most important runtime flow.

16.1 Input resolution
---------------------
On `/query`, the backend receives:

- `query`
- `scope`
- `selected_document`
- session user

`selected_document` is parsed as `scope::filename`.
If present, it can effectively override the generic scope and directly bind the request to:

- shared collection + specific filename
- personal collection + specific filename

16.2 Query logging and audit
----------------------------
Before retrieval starts, the app:

- creates a query log id using the current transaction id
- writes `QUERY` into `audit_events`
- logs query metadata such as scope and selected document

16.3 Orchestration path
-----------------------
If `USE_ORCHESTRATION=true`, the request goes through `QueryOrchestrator`.

Flow:

1. classifier node
   - classify raw query as `direct` or `rag`
   - classification happens before rewriting

2. direct path
   - short in-scope general answer using the LLM
   - no retrieval

3. rag path
   - delegated to `RAGProcessNode`
   - that delegates to `QueryDecompositionOrchestrator`

4. query decomposition
   - planner decides whether the question should be split into up to 3 sub-queries
   - if no decomposition, one sub-query is processed
   - if decomposed, sub-queries run in parallel via `ThreadPoolExecutor`

5. per-sub-query RAG processing
   - rewrite query
   - retrieve chunks
   - compute low-confidence flag from semantic distances
   - rerank chunks
   - generate answer

6. synthesis
   - if multiple sub-queries exist, answers are synthesized into one final answer

7. web fallback decision
   - if `needs_web_scraping` is true, LangGraph routes into the Tavily node
   - for decomposed queries, this only becomes true when all sub-query results are marked low-confidence

8. final response assembly
   - response
   - justification
   - sources
   - route_taken
   - retrieval_debug

9. query history persistence
   - saved in PostgreSQL

10. query log teardown
   - query context variable is reset

16.4 Legacy non-orchestrated path
---------------------------------
If `USE_ORCHESTRATION=false`, the app uses a simpler direct RAG flow:

1. rewrite query
2. retrieve chunks by scope
3. rerank chunks
4. generate answer
5. build `retrieval_debug`
6. save query history

The older Tavily fallback block in this branch is commented out in the legacy path.


17. Query Rewriting
-------------------
Active file: `src/queryRewriter/rewriting_Chatgpt.py`

Responsibilities:

- normalize user wording into insurance-domain terminology
- keep intent intact
- output a single rewritten sentence

Implementation:

- OpenAI client initialized once per instance
- model: `gpt-4o-mini`
- sync method:
  - `rewrite_query_sync(query)`
- async wrapper:
  - `rewrite_query(query)` simply calls the sync method

Practical effect:

- improves retrieval by substituting user-friendly phrases with policy terminology such as:
  - doctor fees -> consultation charges
  - hospital stay -> inpatient hospitalization
  - time before coverage starts -> waiting period


18. Retrieval Layer
-------------------
Active file: `src/retriever/retrival.py`

This class is named `retrivalModel` in the code.

18.1 Initialization
-------------------
At construction it:

- loads `.env`
- creates a `SentenceTransformer` embedding model
- creates a Chroma Cloud client
- initializes an in-memory BM25 cache

18.2 Semantic search
--------------------
Method:

- `semantic_search(rewritten_query, collection_name=None, top_k=15, document_filter=None)`

Behavior:

- encodes the query into an embedding
- queries Chroma by vector similarity
- asks Chroma for documents, metadata, and distances
- computes `semantic_score = 1 / (1 + distance)`
- tags the chunk with `matched_by = ["semantic"]`

18.3 Keyword search
-------------------
Method:

- `keyword_search(...)`

Behavior:

- fetches all chunks from Chroma for the collection/document filter
- builds a BM25 corpus from:
  - document name
  - section heading
  - clause id
  - chunk text
- tokenizes with a regex over lowercase alphanumerics
- scores query tokens with BM25
- returns top positive-scoring chunks tagged `matched_by = ["keyword"]`

18.4 Hybrid search
------------------
Method:

- `hybrid_search(...)`

Behavior:

- runs semantic and keyword retrieval separately
- uses reciprocal rank fusion with `rrf_k = 60`
- merges by `chunk_id`
- preserves both semantic and keyword score fields when available

18.5 Public retrieval method
----------------------------
Method:

- `retrive_Chunks(...)`

Behavior:

- thin wrapper over `hybrid_search`

18.6 Context formatting helper
------------------------------
Method:

- `get_context_string(chunks)`

Behavior:

- converts retrieved chunks into a readable string containing document, section, and content


19. Chunking and PDF Text Processing
------------------------------------
Active file: `src/ingestion/chunker.py`

This module handles prose extraction and section-aware chunk generation.

19.1 Text extraction strategy
-----------------------------
Key behavior:

- `pdfplumber` extracts page content
- table bounding boxes are detected first
- words inside tables are excluded from the prose extraction path
- repeated headers/footers and page numbers are removed
- TOC-like pages can be skipped

This matters because tables are handled separately and later converted into row sentences, reducing duplicate indexing.

19.2 Heading detection
----------------------
Section building depends on `src/shared/heading_detection.py`.

That helper recognizes probable headings using:

- structured patterns like "Section 4 ..."
- numeric patterns like `1.2.3 ...`
- uppercase headings
- title-case short headings
- lines ending in `:`

19.3 Section model
------------------
`_build_sections(text)` produces tuples of:

- `section_heading`
- `clause_id`
- `section_text`

This makes chunk metadata more useful during retrieval and answer justification.

19.4 Sentence-aware chunking
----------------------------
`_chunk_section_text()`:

- splits text near sentence boundaries
- respects a max token budget
- creates overlap by carrying trailing sentences into the next chunk
- hard-splits overlong sentences if required

Current defaults:

- `DEFAULT_MAX_TOKENS = 240`
- `DEFAULT_OVERLAP = 0.15`

19.5 Small-chunk merge
----------------------
`_merge_small_chunks()` merges adjacent chunks if:

- they belong to the same section heading
- they share the same clause id
- combined token size stays within the max budget

19.6 Final chunk IDs
--------------------
Chunk IDs are generated as:

- `<document_name>_<index>`


20. Embedding Layer
-------------------
Active file: `src/ingestion/embedder.py`

Responsibilities:

- create embeddings with `all-MiniLM-L6-v2`
- sanitize metadata for Chroma
- upsert records into Chroma Cloud

Important behavior:

- `upsert()` is used, not `add()`
- this avoids duplicate-id failures when the same chunk IDs are re-ingested

Batching:

- default batch size is `300`

Metadata sanitization rules:

- `None` becomes empty string
- non-primitive values are stringified
- missing document name becomes `unknown_document`
- missing section heading becomes `General`
- missing clause id becomes empty string


21. Ingestion Pipeline
----------------------
Active file: `src/ingestion/ingestionPipeline_Chatgpt.py`

The ingestion pipeline combines prose chunking and table processing.

21.1 Inputs
-----------
Constructor accepts:

- `dataset_dir`
- `collection_name`
- `chunk_output_dir`
- `file_paths`
- `table_sentence_model`

21.2 File resolution
--------------------
Modes:

- explicit `file_paths`
- all PDFs inside `dataset_dir`

Only `.pdf` files are accepted by this active path.

21.3 Parallel per-document processing
-------------------------------------
For each PDF, `_process_single_document()` creates a two-thread executor:

- one thread processes prose chunks
- one thread extracts tables and generates table sentences

21.4 Prose path
---------------
`_process_document_chunks()`:

- chunk PDF text
- optionally write chunk JSON
- embed chunks into Chroma

21.5 Table path
---------------
`_process_document_tables()`:

- extract tables from PDF
- optionally save raw table JSON
- convert table rows into natural-language sentences
- optionally save enriched table JSON
- convert table sentences into chunk-like records
- embed those records into Chroma

21.6 Aggregate outputs
----------------------
If `chunk_output_dir` is set, aggregate files can be written:

- `chunks.json`
- `tables.json`
- `tables_nl.json`

21.7 Table sentence record IDs
------------------------------
Generated as:

22.2 Table-to-sentence generation
---------------------------------
Active runtime file: `src/tableHandling/trialNLSentence_Chatgpt.py`

Purpose:

- convert each table row into exactly one natural-language sentence
- preserve row order and column-value relationships
- avoid summarization/hallucination

Flow:

1. parse markdown table into headers and rows
2. prompt OpenAI with strict one-row-one-sentence rules
3. normalize model output into line-delimited sentences
4. if needed, fall back to chunked table processing
5. store:
   - `nl_sentences`

   - `nl_error_type`

Why this exists:

- many policy benefits/limits are tabular
- prose-only chunking would miss or degrade these facts
- table sentence embeddings make those rows retrievable by natural language


23. Reranking Layer
-------------------
Active file: `src/retriever/reranking_Chatgpt.py`

The reranking pipeline is two-stage.

23.1 Metadata-enhanced similarity reranking
-------------------------------------------
For each chunk:

- embed the query
- embed chunk text
- embed section heading
- compute cosine similarity for:
  - query vs chunk text
  - query vs heading
- combine scores with weights:
  - chunk content: `0.7`
  - heading: `0.3`

Result:

- chunks sorted by `combined_score`

23.2 LLM reranking
------------------
The top metadata-ranked chunks are then passed to `gpt-4o-mini`.

Prompt instructs the model to:

- select only truly relevant chunks
- return chunk indices only

Parser behavior:

- takes first output line
- strips everything except digits and commas
- parses indices
- validates bounds
- falls back to default order if parsing fails

Async note:

- the public async method is only a wrapper around synchronous logic
- there is no true async network concurrency inside this class

25. LangGraph Orchestration
---------------------------
Active file: `src/orchestration/orchestrator_Chatgpt.py`

The orchestration graph uses the following nodes:

- `classifier_node`
- `direct_llm_node`
- `rag_node`
- `web_scraping_node`

Graph shape:

- START -> classifier
- classifier -> direct or rag
- direct -> END
- rag -> similarity/fallback check
- rag -> END or web_scraping
- web_scraping -> END

State fields include:

- original query
- rewritten query
- scope
- username
- collection name
- document filter
- route
- answer
- justification
- sources
- success flag
- route_taken
- needs_web_scraping
- error
- sub_query_results
- metadata

Classifier behavior:

- LLM-based
- default/fallback route is `rag`

Direct node behavior:

- answers only in medical-insurance product scope
- unrelated topics are redirected rather than answered directly

RAG node behavior:

- uses `RAGSubQueryProcessor` through `RAGProcessNode`
- wraps query decomposition orchestration

Web node behavior:

- uses Tavily if available
- returns answer plus list of web sources


26. Query Decomposition
-----------------------
Active file: `src/queryDecomposition/orchestrator_Chatgpt.py`

Purpose:

- split complex multi-part questions before retrieval
- improve retrieval focus and final synthesis

Planner output schema:

- `should_decompose`
- `sub_queries`
- `reason`

Rules enforced by prompt:

- max 3 sub-queries
- only decompose when aspects are distinct
- each sub-query must be standalone

Execution behavior:

- if no decomposition, run one query directly
- if decomposed, sub-queries are run in parallel threads

Parallelism detail:

- `ThreadPoolExecutor`
- `contextvars.copy_context()` is used so logging context survives into worker threads

Synthesis:

- a dedicated LLM call combines sub-query answers into one final answer

Aggregated retrieval debug:

- sums source-type counts across sub-queries
- attaches which sub-query each top chunk came from


27. Reusable RAG Sub-Query Processor
------------------------------------
Active file: `src/orchestration/rag_pipeline_Chatgpt.py`

This class is the core reusable RAG executor for one question or one decomposed sub-question.

Flow inside `process_sync()`:

1. rewrite query
2. retrieve chunks by scope/collection/filter
3. if no chunks:
   - return "No relevant policy content found for this question."
4. inspect semantic distances
5. compute low-confidence flag
6. rerank chunks
7. generate answer
8. return answer, justification, sources, rewritten query, retrieval_debug, distance metadata

Low-confidence heuristic:

- `DISTANCE_THRESHOLD = 1.1`
- if best semantic distance is greater than `1.1`, `needs_web_scraping=True`

Scope resolution logic:

- explicit `collection_name` wins
- else `shared` -> shared collection
- else `personal` -> personal collection
- else `combined` -> concatenates shared and personal retrieval results

Combined-scope note:

- shared and personal results are concatenated before reranking
- there is no explicit deduplication step before reranking in the combined retrieval path

36. Important Behavioral Notes and Caveats
------------------------------------------
The following are not design guesses; they are direct consequences of the current code.

1. The active production path is OpenAI-based.
   - The frontend imports the `_Chatgpt` modules, not the Mistral/Gemini ones.

2. Query classification happens before query rewriting.
   - Small-talk and direct informational questions can bypass retrieval entirely.

3. Async wrappers are mostly sync under the hood.
   - Many `async def` methods simply call synchronous SDK methods.
   - Real concurrency in the RAG path mainly comes from thread pools during sub-query decomposition and per-document ingestion fan-out.

4. Shared/personal file deletion does not delete embeddings.
   - Chroma cleanup is not implemented in delete endpoints.

5. Personal re-upload does not clear prior vectors.
   - The old local file is removed, but the personal collection is not purged first.

6. BM25 cache can become stale after ingestion.
   - The retriever caches keyword corpora in memory and does not invalidate them on upload.

7. Default admin passwords are reseeded at startup.
   - This is operationally important and security-relevant.

8. The frontend "justification" box in chat pages shows source chunk ids and sections, not a polished citation explanation.

9. The app maintains two parallel sources of document visibility.
   - uploaded-files metadata in Postgres
   - actual chunk metadata in Chroma
   - `_get_document_options()` merges both sources

10. The current document selector can scope a query to one shared or personal PDF.

11. Logs are a first-class debugging surface.
   - request logs, query-step logs, and lifecycle reports are all intentionally structured.

12. The shared Chroma helper in the frontend is env-driven, but embedder/retriever tenant/database are hardcoded.


37. End-to-End Mental Model
---------------------------
If you want to understand "what is happening and how it is happening" in one pass, the most accurate mental model is:

1. A user signs in through a FastAPI/Jinja session app backed by Postgres.
2. Admins upload shared PDFs; users upload one personal PDF.
3. Upload triggers an ingestion pipeline that:
   - extracts prose,
   - identifies headings,
   - chunks text,
   - extracts tables,
   - converts table rows to natural-language sentences,
   - embeds both prose chunks and table sentences into Chroma Cloud.
4. A user asks a question.
5. The app logs the request and writes an audit event.
6. LangGraph classifies whether the question needs RAG or can be answered directly.
7. If it needs RAG, the system may decompose the question into smaller parts.
8. Each query/sub-query is rewritten into insurance terminology.
9. Retrieval uses both vector similarity and BM25 keyword matching.
10. Results are fused, reranked by semantic metadata similarity, then reranked again by the LLM.
11. The answer generator reads the top chunks and returns a plain-text answer plus cited source previews.
12. If retrieval confidence is poor, the orchestrator can fall back to Tavily web search.
13. The final answer, sources, and route are returned to the browser and saved into query history.
14. All major phases are logged for debugging and evaluation.

39. Final Summary
-----------------
This project is not just a simple "ask an LLM over PDFs" app. It is a full-stack policy-assistant system with:

- a session-authenticated FastAPI web interface,
- Postgres-backed user/audit/history persistence,
- a Chroma Cloud vector backend,
- hybrid semantic + keyword retrieval,
- section-aware chunking,
- special handling for policy tables,
- LangGraph routing and decomposition,
- optional web-search fallback,
- structured logging and offline evaluation tooling.

The single most important architectural fact is that the live application is driven by `src/frontend/app.py`, and that file wires the OpenAI `_Chatgpt` modules into the end-to-end upload and query flows.
